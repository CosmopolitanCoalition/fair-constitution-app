Additional tradeoffs the operator asked to see: asynchronous commit can reduce WAL-flush waiting but can lose recently acknowledged transactions on a crash, weakening the currently promised durability; it also does not remove random index reads or synchronous work under the global lock. It is not included in the recommended correctness-preserving package. Turning off fsync/full-page protection is a materially greater corruption risk, not a justified fix. Omitting required audits, ballots, repairs or verification would change what “world finished” means; it cannot honestly be sold as a speedup of the same task. Bigger Redis/more CPU has no demonstrated connection to this bottleneck.

**Recommended integrated effort:** develop UUID locality, query-tested index reductions, and broader transactional audit staging together, with chair grouping where the fixture coverage is ready. Independently prepare a properly budgeted shared_buffers correction for an operator-controlled restart/measurement. Then benchmark the package and reattribute remaining time. These are complementary routes toward a large gain; no evidence currently supports promising 10×. Preserve the already implemented election recovery throughout.

PostgreSQL settings are live observations, not changes applied. The 512 MiB cap comes from get-started.sh's explicit clamp, so the memory option needs reconsidering the large-host workload budget rather than claiming the installer failed to apply its current formula. PostgreSQL documents shared_buffers as a server-start setting and explains OS-cache and memory-budget considerations: https://www.postgresql.org/docs/current/runtime-config-resource.html. Asynchronous commit's data-loss tradeoff: https://www.postgresql.org/docs/current/wal-async-commit.html.

The first two alone loaded **59,587 PostgreSQL index blocks** during the sample. These are shared-buffer reads and may be satisfied by OS cache; do not call them all physical disk misses or equate block counts with measured time share. Statistics are database-wide, including other clients, but zero index scans alongside active insert-owner samples strongly points to insert/uniqueness work rather than lookup scans. Many sampled lock holders were in DataFileRead during audit/public-record INSERTs.

Confirmed definitions and new rows:

- audit_log primary key is `(id)`, distinct from the seq index used for the chain head.
- audit_log.id defaults to **gen_random_uuid()**. RepairChairAudit's bulk INSERT omits id; current AuditService append also relies on that default. Twelve recent live audit IDs were all version 4.
- PublicRecordService::publish creates **Str::uuid()** IDs before staging/publication. Twelve recent public-record IDs were all version 4. The unique id index is therefore updated at random positions despite append-ordered seqs.
- LedgerService already explicitly creates **Str::uuid7()** row IDs (`app/Services/Economy/LedgerService.php:107`). This is an existing repository technique, not a new UUID dependency.

**Foundation change 1:** provide time-ordered UUIDv7 IDs for newly inserted audit rows in the chair collector and synchronous repair append paths, and for newly published/staged public records. Prepare IDs before acquiring the global chain lock, carry them through the existing inserts, and retain every old ID/row/hash/reference. Inspect other audited insertion paths for a consistent implementation; do not fix only one new collector while leaving most synchronous repair writes random. No history rewrite or index rebuild should be necessary for forward-only ID generation. UUIDs remain unique opaque identities; preserve seq-based chain order and exact ballot/publication references. Test uniqueness under concurrent workers, hash-chain/rollback behavior and identical reference associations. Benchmark the same index-block deltas and actual repair throughput. **No 10× promise is made before measurement**, but this attacks demonstrated work inside the serialized section.

The actor-only public-record index shares its leading key with profile_publication_seek_idx; its additional write cost is visible too. Treat any retirement as a separate, query-plan-tested follow-up, as with the earlier ledger index work. Do not drop indexes speculatively on the demo.
