## Confirmed competing application workload

At about 04:26 UTC, PostgreSQL showed **25 client sessions running the same CLK-06 residency aggregate, plus 32 parallel workers**. The queries began around **04:18:47** and were still active more than seven minutes later; at 04:26:49, 24 client sessions were waiting on BufferIo and one on DataFileRead. They also held the oldest database snapshots, over 2.7 million transaction IDs behind current work by the later sample.

The SQL maps exactly to `app/Jobs/Clocks/EvaluateCriticalPopulationJob.php`. It is an application job running through Horizon, not the separate Claude monitor. `EvaluateClocksJob::handle` dispatches another such job on each scheduler sweep. The child implements `ShouldQueue` with no uniqueness or execution-overlap guard, and each invocation starts its cursor at the zero UUID. The scheduler's `withoutOverlapping`/`onOneServer` does not protect the lifetime of these separately queued child jobs.

Thus multiple jobs can repeat the same expensive scan concurrently. They compete with Step 5 and retain old snapshots that can delay cleanup of old row versions. The source also puts LIMIT after eligibility filtering and GROUP BY: a 5,000-result limit does not guarantee a short query when few jurisdictions qualify. The measured existence of duplicate sweeps is certain; the size of a resulting simulation speedup remains unmeasured.

## One priority recommendation

**Prevent concurrent duplicate executions of EvaluateCriticalPopulationJob as a focused fix for Step 5 interference.** Keep one real CLK-06 evaluation progressing; coalesce redundant queued/running copies through a tested distributed execution guard, with dispatch deduplication if needed. Preserve the periodic catch-up behavior, future sweeps, threshold resolution, liveness, activation-state and memberless-jurisdiction guards. Do not disable clocks, alter the simulation's institutional rules, pause the whole default queue, or change the 73 simulation workers.

Execution-time protection matters: a dispatch-only uniqueness change does not neutralize copies already in the queue. Lock expiry/recovery must match the actual potentially long runtime and survive failure without permanently suppressing later evaluation. A contending duplicate should avoid the expensive scan and not create a rapid release/retry storm. The developer should choose and test the smallest correct mechanism rather than assume the parent scheduler lock covers it.

Validate two independent workers contending for the same job, queued duplicates, guard release after success/failure, crash/expiry recovery and subsequent legitimate evaluation. Retain tests proving deleted/governed jurisdictions stay excluded and legitimate crossings still reach the ordinary activation path. If bounding a single sweep's query is necessary for the mechanism, preserve source-cursor progress across empty/filtered batches; do not silently skip candidates. Otherwise leave query redesign for measured follow-up.

Secondary evidence retained for later, not a parallel implementation request: `stageSlateNomination` performs appointment, dossier, nomination and seat writes without an enclosing nomination transaction, analogous to D004's governor finding. Consolidating each nomination could reduce commits (116 ms/court currently), but first remove the confirmed duplicate sweep interference and remeasure. The audit wait may then change too.
